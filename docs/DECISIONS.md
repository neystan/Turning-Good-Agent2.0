所有者做出的决定，按时间顺序追加。标注"暂定"的条目可能随后续讨论调整，调整时追加新条目说明，不改写旧条目。

## 2026-10-25 做通用型个人助手

产品是一个通用型 personal agent：用户只需要跟它说话，它负责记住、整理、提醒，复杂的处理都在后台完成。不预先限定某个垂直场景。

理由：MVP 阶段由所有者自己使用，所有者的日常生活就是最真实的测试场景。

## 2026-10-25 新建独立仓库

新建 Turning-Good-Agent2.0 仓库，不在原 Turning-Good-Agent 上演进。

理由：新产品的记忆架构（按状态组装上下文、承诺、时间线）和运行方式（事件驱动、后台处理）与原项目差别较大。

## 2026-10-25 产品原则

- 单一会话：用户不需要管理会话，话题由系统在后台自动分类，使用门槛极低。
- 重记忆、轻会话：多层记忆，上下文压缩对用户无感，长期使用不膨胀。
- 多层主动提醒：除了任务完成后汇报，还会总结日常、主动提醒用户注意某些事。
- 所有重处理放在后台，不影响正常互动。
- 全天候运行。

理由：所有者使用 Claude Code、Codex、Hermes 时，经常遇到冗余汇报、反复解释前文冲突、上下文膨胀难以维护等问题；希望用户体验始终放在第一位。

## 2026-10-25 运行位置与渠道

runtime 是常驻服务，部署在所有者租用的云服务器上，初期可以在本地电脑运行。桌面端和手机端只是接入渠道，关闭它们不影响系统运行。以后计划做桌面应用和手机 App。

理由：主动提醒和后台任务要求 runtime 全天候在线，不能依赖客户端是否打开。

## 2026-10-25 技术选型

- 语言：Python。
- 模型：DeepSeek。

## 2026-10-25 先做 MVP

先做 MVP，跑通一个最简单的 agent runtime，再逐步增加功能。不急着上线，不急着扩展。

## 2026-10-26 runtime 与插件方向（暂定）

- 对话使用极简的 agent loop，在关键节点发出事件；只有任务、承诺这类长生命周期对象才使用状态机。
- 整体采用事件驱动：用户消息、定时器、外部信号、任务完成都是事件。
- 内核极小，其余能力做成插件；扩展点只在有真实需求时开放。参考 Pi、Hermes、DeepSeek harness 的设计。

理由：原 Turning-Good-Agent 的单轮状态机以用户消息为中心，压缩和保存位于回复之前，阶段固定，不适合大量非用户触发的后台工作。所有者暂时同意这个方向，插件系统还需要继续讨论。

## 2026-10-31 单一会话只约束产品界面

用户界面始终只显示一个会话，用户不需要管理会话。这条只约束产品界面，不约束内部执行：模型不需要只看一条不断增长的消息历史，每轮只取这一轮需要的内容。系统内部暂定为多个相互独立的上下文，它们之间可能需要联系，是否联系、如何联系还没有定。

理由：所有者担心把所有任务都塞进一条历史，效果不好，也难以实现。把界面和执行分开后，用户的体验不变，内部实现也不受这条历史的限制。

## 2026-10-31 上下文切换测试提前到 M1

M1 的验证方式增加一项：交替聊多个话题时，旧话题不混入回答，切回旧话题能接上。

理由：这是单一会话体验能否成立的关键，越早发现问题，改动成本越低。代价是 M1 要多准备一组虚构的测试对话。

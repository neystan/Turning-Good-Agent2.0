# 审查规范

本文规定代码审查查什么、怎么写结论。每次提交前按"自查清单"检查本次改动；阶段完成时或所有者要求时，做一次整体审查。

## 自查清单

按优先级排列，前面的问题比后面的更重要。

1. **正确性**：行为是否符合规格和阶段文档；边界情况、异常路径、并发和重启后的状态是否正确。
2. **安全与隐私**
   - 没有提交密钥、服务器地址、账号信息或真实个人数据。
   - 外部内容（网页、邮件、群消息、工具结果）不能直接创建承诺、修改核心档案或触发写操作；写入记忆的内容带有来源。
   - 有副作用的操作经过权限检查或用户确认。
3. **架构边界**
   - 内核没有依赖插件；插件之间没有直接引用。
   - 重处理没有放进回复用户的路径。
   - 上下文按状态重新组装，没有在历史上不断追加；各上下文区块遵守自己的预算。
   - 原始日志只追加、不修改。
4. **简单性**：没有为假想需求增加的抽象、配置项或间接层；没有重复实现成熟库已提供的功能；废弃的代码路径已直接删除。
5. **测试**：新行为有测试覆盖；没有为了通过而删除、跳过或放宽测试。
6. **文档**：STATUS、DECISIONS、规格和架构说明与本次改动一致；新增函数有中文注释。

## 整体审查

整体审查覆盖全仓库，除上面的清单外，还要检查：

- 模块之间的依赖方向，以及是否存在循环依赖。
- 长期运行下的增长：上下文、记忆、日志、任务和索引的体量是否有上限或清理机制。
- 后台任务的可靠性：异常后是否会静默停止，重启后能否恢复。

报告放在 `docs/reviews/` 下，按日期命名，例如 `docs/reviews/2026-11-01.md`。需要处理的问题登记到 [STATUS.md](STATUS.md) 的待办中跟踪。

## 结论的写法

每条发现包含：

| 字段 | 说明 |
| --- | --- |
| 等级 | H：会导致数据丢失、安全问题或功能失效；M：特定条件下出错，或明显违反架构约束；L：可维护性问题或小缺陷 |
| 位置 | `文件路径:行号`，并写明基准提交 |
| 现象 | 代码实际做了什么 |
| 影响 | 会造成什么后果，在什么条件下发生 |
| 核实状态 | **已核实**：已读过实现和调用方，确认行为属实。**推测**：依赖未验证的环境、时序或外部服务 |
| 建议 | 最小的处理方式 |

只审查、不修改：审查过程中不改产品代码，修复另行提交。
